## 计算总式
`final=clamp(sum(one score per DISTINCT selected physical palace after void) + eligible_control + auspice + weak_drain - (five_not ? 2*distinct_palace_count : 0), -5, +5)`。
每宫先对驻宫星、门、神、81 天地格和被选中的不同天干独立加总，再一次 `clamp(-5,+5)`，再门破降两级（若非例外），再真/假空吉减3或凶加3；最终宫分才汇总。相同乙角色/同实宫不能再次累加宫分；符合特别条件的乙丁一组、独立天心、独立值符条件另外加分，不是第二份宫分。伏吟/反吟只表达缓急，不加分。

## 必须公开给下轮开发的尚未解决问题
1. **施力强弱与吉凶符号混同**：`special_disease_control_points` 以 `abs(attacker_score)>1` 作强弱门槛。艮八宫最终 `-5极大凶` 就因其绝对值为5，被认为是有力施力方而额外加3；这不是用神自身的200格/月令旺衰/落宫施力强度证明。应先按已核源表明确区别**力量**和**吉凶方向**，再修正 Python 与 Swift；不能直接凭正负号或绝对值假设。
2. **克病资格门槛可能被旁路**：Python 构建了 `role_effectiveness_gates[*].score_eligible/control_ability`（原来只接受能/艰难），但 V7.8 加分循环只按 `relation=='克'`、绝对宫分、空/受制判断，不检查 `score_eligible`；Swift 也构建 `active` 后在汇总时并未用它约束克病加分。应以最新用户“空/被克仅+1”与源5×5能力表共同建立清晰的资格/降档优先级，不能擅自恢复一条曾与用户冲突的旧门槛。
3. **吉助宿主范围需校准**：当前 `auspice_hosts` 仅 illness/patient/hour/natal/gender，不含 doctor/medicine/chief。某些医生/医药仅独立落宫的情况无法走该同宫天心/乙丁检查；是否符合“所有实际选中用神宫”的最新用户定义，须以具体正反例确定，避免把天心因本身所在宫必定产生固定额外+3。
4. **病宫+5不等于病本身吉**：案例B离九宫合并后+5，源于生门、天地格和乙等混合要素；天芮自身在同宫实际-2。客户断词“病宫极大吉”仅是宫的符号净分，并不能等同“病势本体已经很轻”，且医者兑七-5、患者震三真空0。需要在总结明确分开“病星力量/病势吉凶”与“驻宫总吉凶/受制条件”，不得由宫分直接解释现实病情。
5. **V7.8 检测是自洽而非规则正确性验证**：两张 Python 与原生 Swift 全文相同、单元测试断言同一个公式，但不能证明公式概念没有重复或强弱门槛科学/专业正确。本轮**没有更改计分程序、旧模板、源数据**，**V7.8 两个 +3 均保留为待用户审查的历史输出**，不能默认为新版验证通过。
