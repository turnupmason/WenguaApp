# 婚姻V1.5：从原作者证据链到真实节气月、干支日应期

## 这轮已实际运行的部分

此次不再以用户贴出来的“成或不成”固定模板作断言。程序实际读取了《开悟之门》分析判断章第三节“奇门定应期的主要方法”完整的20条原书方法（原文、行号、hash），依不同条件分为成功类8项、失败类6项、截获寻找专门法3项、方法限制与错例3项。事件**必须先经过**用神、格局和反证的传统成败判断，才能为已经存在的结果选择适用应期法。子丑月填冲空只能提供可审查的触发窗口，不可脱离结果条件当万能“恋爱必成”。

## 一次完整的原著历史计算：王大妈问儿子婚期

来源：`sources/kaiwu/开悟之门_恋爱婚姻预测.txt`，案例`kaiwu.marriage.case01`（1998-11-09）。书中作者的先行判断在第39行从乙庚和日时关系论婚事可成，第41行从双方真实年命与父母宫论促成，第43行补六合空亡和“甲申旬午未空、子丑月冲实”以及内盘论时速；**第45行才报告真实结局，前43行的算法不能提前访问第45行**。

以真实太阳黄经（中国当地时区、30度一个节气月，非公历12月/1月）计算：

| 作者原定应期 | 推算出的实际北京时间范围 | 不参与初始择期的后续反馈 |
|---|---|---|
| 子月（冲午空） | 1998-12-07 约15:53—1999-01-06 约03:06 | 12月16日办理结婚证，确在子月（甲子月丁酉日） |
| 丑月（冲未空） | 1999-01-06 约03:06—1999-02-04 约14:46 | 1月17日举办婚礼，确在丑月（乙丑月己巳日） |

**这个验证不是作者预测了12月16日或1月17日。** 作者原文给出的是子丑两个可能月份；后验日期恰好分别落入两个月。日干支计算也与书内记录一致，能证明书源应期法至少已被真正转成可执行月份计算，但不能证明它对新盘的命中率。

源码`src/wengua/astro_calendar.py`包含离线Meeus/NOAA太阳黄经算法和可选Swiss Ephemeris比较，`src/wengua/book_timing_runtime.py`实行“首断之后才求应期”的方法择取、候选和事后反馈严格隔离。适用的原书成功类规则在分析判断章第184行，失败类不同，尤其第199行对空亡应空失败不能混成成事。这是书内的**条件化方法**，不是给所有问事统一套同一个时间。

## 新的实际盘面 JSON 接口

沿用`scripts/run_marriage_json_study.py`及`docs/MARRIAGE_RUNTIME_JSON_V1_4.md`，在`calendar_inputs`中增加：

```json
{
  "day_ganzhi": "癸酉",
  "solar_term": "芒种",
  "hour_ganzhi": "丁巳",
  "year_ganzhi": "乙亥",
  "month_ganzhi": "壬午",
  "local_time_iso": "1995-06-11T10:00:00+08:00",
  "iana_timezone": "Asia/Shanghai"
}
```

此为**原书起盘练习盘**的历法自洽校验输入，不代表实际恋爱占断。程序独立计算四柱与节气，再复核原九宫，中五宫不填不存在的门神星；任意篡改日干支、月份、起局局数或宫位，均按最先命中的规则被拒绝。若当前盘中六合宫确有旬空分支，则可基于该时刻连续计算此用神条件下未来填实/冲实的节气月候选；若六合宫不空，必须不能自动套原书空亡规则。候选月≠最后应期，必须先判用神和问事实际成败；目前不能将22场景视为通用保证准确的预测算法。

## 六层真实阶段门槛

第一层起盘已能在给定真实IANA时刻且不处日界争议与节气边界含糊时，实际计算和原局复核；第二层24项已逐一检查，但不是所有古籍中含条件的特殊格局都有正确的可执行实现；第三层可将当事人的年命对应到天盘候选宫，仍须对不同问事选择主次及对照作者例；第四层已从数据库存原著起盘、婚姻案例和20种应期规则，严格隔离后验反馈；第五层已能用特定**原书作者已先断成事**的历史案例计算两个月应期，但尚不能在所有未知新盘自动形成完整综合成败；第六层仅在上述真正完成后让GPT将结果人话表达。不能声称已经对陌生人婚姻事件给出经过验证的唯一日期。
