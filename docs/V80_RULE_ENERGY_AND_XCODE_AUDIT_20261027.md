## 下一阶段操作顺序（不更改冻结 V8.0 两例）

1. 为 **任意符号组合** 而不只是医生+乙、值符+乙，创建抽象 `role_key / kind / symbol_id / palace_id / energy_fact_id` 与关系图模型。用8种疾病角色互相同宫、双宫、三符号相邻/同宫、空亡、宫克、墓刑的排列测试：同符号不同角色只算一次自身分、不同符号必逐个看真实源强、同一宫基础只累加一次；单独列出“有独立受助者”的专题触发证据。不可为满足新组合改变已经验收的两例，未经用户审核的新计分写 V8.next 实验候选，而非偷偷替换当前 V8.0。
2. 将“宫生病”“病生本方”“同五行比和”明确区分**事实方向**和**效果是否能由权威来源判定**；特别是弱病泄耗固定+3，必须找现有用户规则/古籍给出可量化额外门槛才上线新分。
3. 对全量624 Python 测试的22失败建立原因分类表（过时历史断言、公开文本错、真正源矩阵差异、条件人物绑定问题）；原失败输出保留，修历史测试为只读版本 fixture 而非删除/跳过；所有实时引擎不再靠旧版分数断言回归。
4. 未来各领域需要不同 `DomainProfile / SignifierRole / RelationRule / Priority / TimingTrigger / EvidenceConflict`，按《神奇之门》《开悟之门》逐领域真实例案核准。婚姻（乙庚、六合、值使、月日太岁、入墓击刑、伏吟反吟）与疾病不能共用“天芮+3”的分数框架。其他领域尚未验证，不得默认支持。
5. 后续 UI 开发直接使用现在 XcodeGen 工程，按用户现有五行颜色、九宫格、空马墓及可展开宫详情与实际 V8 断词做，不推倒重来。对下次 UI 变更继续 macOS 真 Xcode 编译和资源校验；真机测试、存档迁移及隐私数据处理与当前软件逻辑测试明确分开。
